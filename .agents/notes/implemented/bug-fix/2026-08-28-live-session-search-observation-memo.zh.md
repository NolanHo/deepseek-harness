# Agent Note: 搜索对活跃会话观察的记忆化

状态：implemented

[English](2026-08-28-live-session-search-observation-memo.md) | 中文

## Problem

会话搜索在**每次搜索**时对**每个附加会话**重算完整观察——全量事件 `structuredClone`、共享文档提取、整日志 `JSON.stringify` 与 SHA-256，然后才比对指纹。大型附加日志（55.3 万事件的对话、69.2 万事件的会话）让每次搜索在未变化的数据上烧掉 ~12-13 核心秒；而 SQLite 索引对账本身已经是增量的。

## 决定

按“事件数 + 尾 seq/time”为键记忆化每个会话的活跃观察。附加日志只会追加（表面替换、steering、编辑也都是追加），该键即可标识观察内容；未变化的会话复用上一次的克隆、文档与指纹。已分离会话的条目在每次稳定观察结束时驱逐，使记忆化集始终有界于附加集。发生变化的会话仍需一次完整重算（这是全日志指纹设计的成本下限）。

## 后果

- 未变化的附加会话重复搜索只付索引查找成本（47 ms 路径）；发生追加的会话仍需一次完整重算（成本下限不变）。
- 记忆化位于观察层，存储、索引与线上格式均未触碰。

## 备选方案

- **指纹增量对账**：全日志 SHA 是该设计的完整性锚点；增量摘要会改变"未变化"的含义，属于线上格式决策而非本缺陷修复。
- **按 mtime 缓存**：追加式变更不保证 mtime 粒度，且部分文件系统上表面替换可在同一 mtime 下原地重写。

## 验证

- 无密钥单元测试断言：对未变化的活跃会话重复搜索时 `structuredClone` 零调用；追加会失效记忆化（新内容被找到）。
- 基于生产存储的独立复现：55.3 万事件的附加会话首次搜索 2420ms（一次性建索引），之后每次重复搜索 **47ms**；无记忆化时每次搜索都全额重付。
