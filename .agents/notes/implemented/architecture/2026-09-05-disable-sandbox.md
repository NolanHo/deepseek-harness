# Agent Note: Sandbox capability disabled in the fork composition

Status: implemented

English | [中文](2026-09-05-disable-sandbox.zh.md)

## Problem

The fork deploys only danger-full-access and never confines, so the sandbox machinery — the sandbox service, its policy provider, the sandboxing bash/pwsh/fs executors, and their unit suites — is pure cost in this fork: composition surface to keep alive, runners and landlock/windows-acl tests that can only trip on deployment hosts, and a permission preset table nobody consumes. The owner decided (2026-09-05, recorded in FORK_CHANGES.md) to disable the sandbox capability from the fork composition, hand the `ctx.shell`/`ctx.fs` slots to the local providers, and stop running the sandbox-area tests.

## Decision

`packages/bundle/base/cordis.patch.yml` (the one layer every dsh profile mounts) carries the whole change; no sandbox package source is edited, so upstream syncs stay zero-cost. `verify-cordis-config` requires every bare plugin a bundle patch names to be a declared dependency of the bundle, so `packages/bundle/base/package.json` gains the two newly mounted local packages (`dsh-bash-local`, `dsh-pwsh-local`; `dsh-fs-local` was already declared) and `pnpm-lock.yaml` records the importer delta.

- Rows `sandbox` (`@deepseek-ai/dsh-sandbox-local`) and `sandbox-policy` (`@deepseek-ai/dsh-sandbox-policy`) are set `disabled: true`, configs retained for a clean re-enable.
- Executor rows `bash-sandbox`, `pwsh-sandbox`, and `fs-sandbox` keep their row ids and their `!!js` platform `disabled` expressions — overlays and the base bundle spec's platform-gate assertions keep addressing them — and only the mounted package changes to the local provider: `@deepseek-ai/dsh-bash-local` (config `timeoutMs: 60000` preserved), `@deepseek-ai/dsh-pwsh-local`, and `@deepseek-ai/dsh-fs-local` (config `cwd: process.cwd()`, the sdk-minimal precedent). Each of those packages registers the capability Service (`ctx.shell` / `ctx.fs`), so exactly one executor/backend mounts per host exactly as before.
- Row `permission` (`@deepseek-ai/dsh-permission-presets`) is set `disabled: true` with it: the service constructor rejects composition over a non-confining executor (`ctx.shell.sandboxMode === undefined`, asserted by its own "rejects composition over a non-confining executor at load" suite), and with bash-local mounted every profile would otherwise fail boot. Row `approval` stays mounted untouched: the approval service has no sandbox dependency, and no tool requests approval once escalation fields are unadvertised.
- Consumer degradation is capability-driven, not code-dependent: `tool-bash` and `tool-fs` read `ctx.shell.sandboxMode` / `ctx.fs.sandboxMode`; the local providers report `undefined`, so `sandboxPolicy` is never fetched and the `sandbox_permissions`/`justification` escalation parameters are no longer advertised in tool schemas or prompt copy. `captureDelegatedPolicyOverrides` reads `ctx.get('sandboxPolicy')?.overrideOf(...)` — already optional. `terminal-bash`/persistent shells hard-inject `sandboxPolicy`, but no base-based profile mounts them; only the sdk-minimal profile does, and sdk-minimal is its own complete tree that keeps its danger-full-access sandbox-policy row (out of scope for this change).
- Root `vitest.config.ts` stops collecting the disabled suites: `forkDisabledSandboxTests` excludes `packages/sandbox/*/tests`, `packages/shell/bash-sandbox/tests`, `packages/shell/pwsh-sandbox/tests`, and `packages/fs/fs-sandbox/tests` from the top-level and thread-safe project exclusions, with the restore path in the comment (re-enable/revert the base rows, delete the list). `forkDisabledSandboxCoverageExclusions` drops those packages' sources from the per-file coverage gate, since their unit suites were what held 100%. The local counterparts' suites (`bash-local`, `pwsh-local`, `fs-local`) stay included — after the swap they are the tested backends. TypeScript typecheck still compiles the excluded packages' sources and tests (repo convention; the exclusion is collection-only).
- The other collection lanes follow the same fork decision. `vitest.e2e.config.ts` excludes the sandbox-family e2e suites (the same four package families as the unit list, `*.e2e.ts` instead of `*.spec.ts`). `vitest.web.config.ts` excludes the `settings-chrome` and `permission-policy-context` browser suites, whose expected/recorded goldens (`apps/web/tests/expected/settings-chrome/`, `snapshots/web/permission-policy-context/`) hard-assert the Permission settings row and the current-sandbox-policy context the fork no longer mounts. `apps/web/tests/shipped-composition.e2e.ts` replaces the upstream sandbox-policy and permission-presets mode pins with absence assertions (`ctx.get('sandboxPolicy')` / `ctx.get('permissionPresets')` resolve `undefined`), so the shipped-composition contract stays fork-true; approval remains pinned to `ask`. `vitest.e2e.config.ts` additionally excludes the ACP escalation suite (`apps/cli/tests/profiles/acp/tests/escalation.e2e.ts`): its denial→escalation flow needs a confining executor the fork no longer mounts, and the suite's keyless smoke describes the upstream composition (the comment notes that keeping that smoke means splitting the file). `vitest.web.config.ts` additionally excludes `access-confirmation` and `seeded-history`, whose Access-mode picker and `/permission read-only` chip assert the same removed permission surface, and `approval-composer`, whose recorded approval takeover is reachable only through that Access-mode chip. `vitest.expected.config.ts` excludes `subagent-inheritance.expected.e2e.ts` (read-only delegation events, sandbox-policy prompt context, denial output) and `image-offload.expected.e2e.ts` (the `Current DSH file policy` runtime-context sentence, whose only producer is sandbox-policy), plus the five whole-normalized-session suites `goal`, `headless`, `semantic-checkpoint`, `subagent-diagnostic`, and `workspace-context-resume`, whose goldens open with the `permission/preset`/`sandbox/mode`/`approval/policy` rows and sandbox:policy runtime-context message the fork log lacks. The snapshot lane stops collecting `snapshots/acp/acp.snapshot.ts` (Consequences below). `apps/cli/tests/windows-shell.spec.ts` asserts the sandbox/permission rows disabled instead of enabled.

Restore path (also recorded in the patch comments): clear `disabled: true` on `sandbox`, `sandbox-policy`, and `permission`, revert the three executor rows' `name` to the `@deepseek-ai/dsh-*-sandbox` packages, delete the vitest exclusion lists (root `vitest.config.ts`, `vitest.e2e.config.ts`, `vitest.web.config.ts`, `vitest.expected.config.ts`, `vitest.snapshot.config.ts`), restore the upstream sandbox/permission assertions in `apps/web/tests/shipped-composition.e2e.ts` and the windows-shell permission-row loop, and re-record or re-sync the ACP snapshot corpus.

## Alternatives considered

- **Keep the sandbox rows composed with danger-full-access defaults** — the smallest diff, but it keeps sandbox runners and approval machinery mounted in a deployment that never confines, which is exactly the friction the decision removes; also the sandbox-policy rows' mode would come from `DSH_PERMISSION_MODE`, an env the fork deployment does not want to rely on.
- **Keep `permission` mounted and edit `dsh-permission-presets`** to tolerate a non-confining executor — that is upstream-owned behavior change outside the write-set, and a preset table bundling sandbox modes has no consumer in a sandbox-less fork; disabling the row is the fork-shaped answer.
- **Rename the executor rows (`bash-sandbox` → `bash-local`) instead of swapping names in place** — rejected: `packages/bundle/base/tests/base.spec.ts` pins platform `disabled` expressions on exactly the `bash-sandbox`/`pwsh-sandbox` row ids (and the test file is upstream-owned, outside the write-set), and keeping ids stable also keeps any user-profile overlay addressing them valid.

## Consequences

- Model-facing tool names and semantics are unchanged (bash/fs/read/write/editor behave identically through the local providers); the model-visible deltas are the disappearance of the `sandbox_permissions`/`justification` escalation parameters, the escalation sentences, the sandbox-policy runtime-context sections, and the `sandbox: {mode, denied, …}` fields on bash results (tool-bash attaches them only when the executor reports sandbox info). One sandbox sentence survives: tool-bash and tool-pwsh descriptions still carry the unconditional marker sentence starting 'Commands may run under a file sandbox; a blocked file operation is reported as `[sandbox: file access denied under <mode> mode]`…' even with no escalation modes (packages/shell/tool-bash/src/index.ts:77 and packages/shell/tool-pwsh/src/index.ts:111) — upstream copy not gated on the executor, so it stays until upstream gates it.
- The permission surface (host `/permission` command, `permissions` session projection, web permission settings row) is absent from base-based profiles; the client permission-presets package renders nothing without the host service. The shipped-composition e2e asserts the absence of `ctx.sandboxPolicy` and `ctx.permissionPresets` in the shipped composition, and the browser suites that exercised the permission UI (`settings-chrome`, `permission-policy-context`, `access-confirmation`, `seeded-history`, `approval-composer`) are excluded from the web lane with their goldens until the rows are re-enabled. The expected lane's assembled-session goldens have the same upstream shape, so `subagent-inheritance`, `image-offload`, and the five whole-session suites (`goal`, `headless`, `semantic-checkpoint`, `subagent-diagnostic`, `workspace-context-resume`) are excluded with them — a real full-lane run on the fork measured 12 failed / 25 across exactly those five whole-session suites before the exclusion, because their whole-session equality diff shifts every later event once the rows are missing. The snapshot lane stops collecting `snapshots/acp/acp.snapshot.ts`: six of its eight replays (the escalation trio plus `cancel`, `cancel-tool-calls`, and `image-compaction`) fail on the fork composition because their recorded sessions pin sandbox/approval events and class tool-schema headers sourced from the escalation-approved sidecar, while the suite's fixture invariants (every scenario directory must stay registered, and escalation-approved doubles as every ACP class's header-pin/schema owner) make a scenario-list exclusion impossible — only handshake and reject-extra-dirs replay green, and they cannot be registered without the pin owner. Re-enabling the sandbox needs an explicit `disabled: false` and the original provider `name`s; an overlay patch cannot clear the base's sticky `disabled: true` or re-match the swapped names (the reasoning is in the vitest.snapshot.config.ts comment), so the upstream-recorded corpus stays excluded until the rows are restored or an upstream-shaped corpus is re-synced.
- The sdk-minimal profile is untouched and still composes the sandbox-policy row in danger-full-access; disabling it there is a follow-up if the fork ever ships that profile.
- A profile-boot run from a fresh worktree needs `pnpm run typecheck` (host `lib/` build) first; the loader resolves `./typert` contributors from built `lib/`.
- Verified: `pnpm run typecheck` exit 0; `dsh --profile headless --dump-config` shows `sandbox`/`sandbox-policy`/`permission` disabled and the local mounts on the executor rows; `vitest list` collects none of the excluded families; base bundle spec green. Follow-up (F1) checks: `vitest list --config vitest.e2e.config.ts` collects none of the sandbox-family e2e suites, and an explicit `vitest run` of those files over the e2e config reports no test files; with built client artifacts, `vitest list --config vitest.web.config.ts` lists neither `settings-chrome` nor `permission-policy-context`, and `vitest run --config vitest.web.config.ts apps/web/tests/shipped-composition.e2e.ts` passes all 3 tests with the fork absence assertions. The affected local suites (fs-local, bash-local, tool-fs, tool-bash, subagent/subagent) are green except a root-environment search-permission denial test (uid 0 cannot be denied directory search) and three real-Claude-CLI fixture tests — both reproduce identically on an unmodified master control worktree, so they are baseline environment failures, not regressions from this change. Unrelated trio (tool-fs-search, session-title, storage-json) green; spill-local's cleanup-sweep failures also reproduce on master. Real-API bash round trip not run (no `DEEPSEEK_API_KEY`). Follow-up (F2) checks after the lane completion: `apps/cli/tests/windows-shell.spec.ts` runs 6/6 green with the fork assertion split; `vitest list` collects none of the excluded suites in any lane (web lane keeps `shipped-composition`; e2e lane keeps zero escalation suites; expected lane lists neither excluded file; snapshot lane lists no `acp.snapshot.ts`); `pnpm run typecheck` exit 0. Round-2 follow-up (F3) — the checks that caught the list-only gap: on 978917e833 (before this exclusion) a real `vitest run --config vitest.expected.config.ts` reproduced 12 failed / 13 passed (25), all failures in the five whole-session suites above and all golden-only row diffs; after the exclusion the same full-lane run is 3 files / 7 tests, all green (exit 0), and `vitest list` under the expected and web configs shows none of the seven expected files or `approval-composer` (the web lane keeps `shipped-composition` and the remaining composition suites).
