# Agent Note: In-place history rewrite for edit-and-resend — durable log truncation at a turn boundary

Status: implemented

English | [中文](2026-09-12-in-place-history-rewrite.zh.md)

## Problem

The `dsh-rewind` plugin's button forked a NEW session on click, but the user wants in-place edit: put a historical user message's text into the current session's composer, edit it, and send — the same session id then discards the armed message's turn and everything after it and continues at the cut. The plugin cannot perform this itself: it has no host half, `ctx.agents` exposes no disposal, and agent lifetime is fiber-owned. Truncation needs the persistence write handle and a disposed agent, so the rewrite runs on the host, atomically with prompt admission.

## Decision

The rewrite happens on the host, atomically with admission, and the intent travels on the prompt request (`rewriteFrom`), not a staging RPC — one operation, one settlement point, no stale host state to cancel, no server-restart loss. `commands.prompt` validates the armed anchor against the stored log through the fork module `resolveRewriteCut` (queue-only; the live Agent must be idle with an empty inbox; subagent-owned Sessions refuse), disposes the Agent (`disposeAgent` releases the persistence write handle), truncates the stored log through a write handle, and resumes the Agent; the response flags `rewrote`. The cut is the seq of the last `turn/start` at or below the armed `user/message`, extended backwards over that message's own admission `agent/inbox/spliced` inserts only (another message's admission is not this rewrite's to discard) — a turn boundary, never mid-turn (a mid-turn cut would make resume append synthetic interrupted-turn closers into the new history), never into the fork-inherited prefix, and never leaving the replaced message's admission bookkeeping behind: the insert carries the replaced text, which the client renders as the user bubble, while its removal splice lands inside the discarded turn. A message queued while an earlier turn was still running keeps its admission insert inside that earlier turn, which the cut retains (the walk cannot cross the committed `turn/end` between them, and a middle event cannot be removed by truncation): the rewrite appends one removal splice for it, so folding the retained prefix leaves no pending inbox entry and the resumed driver cannot replay the replaced message. The rewrite also discards the Session's projection-cache record, and the cache's read paths now refuse rows at or past the durable prefix they would seed — the cache may be behind a log, never ahead of it, which a log that moves backwards would otherwise break. The persistence seam carries the capability as the optional `SessionHandle.truncate?`: a backend that cannot rewrite a committed log omits it, and the consumer fails loud (`session/rewrite-unsupported`). The fork's SQLite backend implements it; the shipped JSONL backend omits it.

The client never intercepts the send path: the armed value lives in the per-session input machine beside the draft (`InputState.rewriteFrom`/`setRewriteFrom`), the native submission carries it, it clears with the committed draft and restores with it on a failed send, and the submitting client rebuilds its window (`resync()`) when the host reports `rewrote === true`. When an armed prompt is admitted without `rewrote` — version skew with a not-yet-restarted host — the settlement is a visible `session/rewrite-missed` failure, never a silent append.

## Mechanism

- **Persistence**: `SessionHandleTruncateOptions { signal? }` and the optional `truncate?(toSeq, options?)` on the seam; the SQLite backend's `truncateLog` deletes rows from the cut, rewrites the one packed row spanning the cut so only its members below it survive, bumps the stored revision once (FTS and projection caches reconcile on revision difference), and rolls back on failure; the handle re-bases its cursor, and its shrink guard keys on the stored revision so the handle's own rewrite reads through as the new shorter log.
- **Host**: `resolveRewriteCut` is a pure function over the observed header, events, armed seq, and `inheritedEventCount`; idempotency precedes every rewrite step — a retried requestId a live Agent already holds resolves `{ accepted: true }` without rewriting again.
- **Client**: `ClientSession.prompt` puts `rewriteFrom` on the wire request and rebuilds before resolving on `rewrote === true`; the follow stream silently drops events at or below its cursor, so the explicit `resync()` is the only trusted rebuild.
- **Inbox repair**: `planInboxRepair` folds the retained prefix's splices exactly as the inbox projection does, finds the armed message's pending index, and returns the one `outcome: 'canceled'` removal splice the rewrite lands through `SessionHandle.truncate`'s `append` option — the discard and the landing batch commit in one transaction, because a repair left to a second append would expose the shortened log without it after a crash. The replaced text itself stays inside the retained insert — a contiguous truncation cannot delete a middle event — but it is balanced: no pending entry, no `user/message`, no replay.
- **Projection cache**: the rewrite calls `SessionProjectionCache.discard(id)` after truncation (best-effort invalidation for the zero-I/O listing read, which has no log to check the rows against), and the seed reads (`hydratePrepared`, `coldSnapshot`) validate the stored rows against the durable prefix they would be folded into. A row at or past that prefix was folded from events the current log does not contain, so it is not a seed: seeding it restored a removed message as a queued item and replayed it as a new turn (observed on the second instance before the rule landed).
- **Client-visible lifecycle**: disposing the Agent removes its session from the store, which the controller relays as `api-session/removed`; the removal hold (`src/fork/rewrite-hold.ts`) defers that announcement across the dispose-to-rebuild window, so clients keep the row, the selection, and the rendered conversation instead of falling back to the new-Session frame ([why](../bug-fix/2026-09-13-rewrite-removal-hold.md)).

## Alternatives considered

- **Client interception of the send path.** Rejected: the armed intent must ride the native submission — an intercepting layer forks the send path, owns its own stale state, and any submission surface it misses silently appends.
- **Truncate at click time.** Rejected: the product decision is truncate-at-send; nothing is written to the database until the prompt is sent, and the armed value lives beside the draft so a cancel costs nothing.
- **Plugin-side bypass writing the store.** Rejected: the plugin has no host half and no persistence access, and agent disposal is impossible from the plugin because agent lifetime is fiber-owned.

## Consequences

- The durable log admits exactly one committed-log rewrite path: host-initiated, at a turn boundary, with no live writer (single-writer ownership plus a disposed Agent), never into the fork-inherited prefix.
- A backend without the capability fails consumers loud (`session/rewrite-unsupported`); JSONL does not implement `truncate`, SQLite does.
- A running turn or a pending inbox refuses the rewrite instead of cancelling someone else's work; a committed rewrite has no UNDO.
- The edited draft is plain text: the replaced message's attachments and reference chips are gone by design.
- The armed value is per-Session input-machine state, so a browser reload disarms the rewrite while the composer draft (persisted per Session) survives: the restored draft then sends as a plain append, with no banner and nothing lost, and the user re-arms by clicking the message again. Observed on the second instance.
- The stored `revision` bump invalidates the FTS index and the projection/checkpoint caches keyed on it.
- The projection cache's row watermarks are a seed floor only while a log only grows: after a rewrite, rows at or past the cut are refused by the cache's own reads and discarded by the writer.
- A rewrite writes two kinds of durable event: the truncation, and the one inbox removal that balances a retained admission insert. Both are appends at the cut; neither fabricates conversation.
