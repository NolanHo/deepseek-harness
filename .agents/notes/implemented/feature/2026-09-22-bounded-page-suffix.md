# Agent Note: Bounded paged history reads — an older page reads only its own span

Status: implemented

English | [中文](2026-09-22-bounded-page-suffix.zh.md)

> Scope: how the fork's paged history read bounds its physical suffix read, what the store guarantees when a bound is present, and why a short suffix is never served as a page. [FORK_SURFACE.md](../../../../FORK_SURFACE.md) owns the divergence's re-apply procedure; [packages/session/session-persistence-sqlite/README.md](../../../../packages/session/session-persistence-sqlite/README.md) owns the operator-facing read contract.

## Problem

The Web GUI's "Load earlier" asks for a page that ends at the oldest record the reader already holds (`beforeSeq`) and carries the log cursor it last saw (`throughSeq`). The fork's `readIndexedSuffix` computed the page's exclusive end for that request — `end = min(throughSeq + 1, beforeSeq)` — and used it to find the message cut, but the suffix read itself was unbounded: `SeekablePersistence.readFrom(id, fromSeq, signal)` reached `SqliteStore.loadStoredFrom`, which ran `SELECT … FROM events WHERE session_id = ? AND seq >= ? ORDER BY seq` and decompressed every row from the page cut to the end of the log. Measured on this deployment's 67k-event Session, the rows decoded per "Load earlier" grew from 348 to 1345 with page depth while the page needed a few dozen of them.

The consumer's request validator made the read's shape visible from the other side. It compared the read's tail with the request cursor (`throughSeq`), a check that only holds while the read runs to the log's end. A bounded read ends at `beforeSeq - 1`, below `throughSeq`, so the validator was really asserting the absence of the very bound this change adds.

## Decision

**The bound is a SQL predicate on a physical row's first logical seq.** `resources/sql/select-events-from-through.sql` adds `AND seq < ?` to the released suffix statement, registered in `src/sql.ts` beside it; the unbounded statement stays for unbounded reads. A caller-supplied `throughSeqExclusive` reaches `physicalSpanFrom` unchanged, so a row is selected when its FIRST logical seq precedes the bound.

**A packed row straddling the bound is read whole and filtered per logical event.** Packed rows represent up to `MAX_PACKED_ROW_MEMBERS` consecutive delta events under one physical `seq`, and that column holds the first of them; there is no bound that selects "part of" such a row. Both arms of `loadStoredFrom` therefore apply the same upper filter they apply to `fromSeq`, which drops the members at or past the bound after the decode.

**A bounded scan that stops below its bound re-runs unbounded.** `scanRows` classifies an undecodable or non-contiguous row as removable when no later valid `turn/end` exists, and as committed corruption when one does. A scan that never reads past the bound cannot see a `turn/end` above it, so it can under-report damage: the bounded scan returns a torn tail where a whole-log scan raises `corrupt session log: invalid committed physical row at seq N`. When `tornFrom < throughSeqExclusive` the read therefore re-runs unbounded and returns that result filtered to the bound — never the short suffix. This keeps "no silent short page" true for every bound and makes the whole-log classification authoritative for damage strictly below the bound, at today's cost only in the rare case of a torn row below it. Damage at or above the bound stays unread, and that asymmetry is intended: a bounded read never reads at or above its bound, so `loadStoredFrom(id, 0, 4)` answers `[0, 1, 2, 3]` where `loadStoredFrom(id, 0)` raises `invalid committed physical row at seq 4` — an older page must not pay for, or fail on, a tail it never serves.

**A bounded read reports the stored end it observed.** The read's own window ends below the client's cursor, so it cannot answer the released cursor checks. `resources/sql/select-max-seq.sql` answers `COALESCE(MAX(seq), -1)` from the `(session_id, seq)` primary key without touching a row body, and `scanStoredPrefix` runs it inside the same read transaction that selects the span — only when a bound is given, so the unbounded read keeps its released statement set exactly. The value travels as `storedEnd` on the store's suffix, the SQLite plugin's `readFrom`, and the fork's `SeekablePersistence.readFrom`: the highest stored logical seq this read observed, `-1` for an empty log, and the whole validated prefix's tail for an unbounded read.

**The plan refuses to cut a page from a suffix that cannot prove its bound.** `readIndexedSuffix` returns `undefined` when the end is at or below the window start, and it accepts a bounded suffix only when its last event is `end - 1` — the store's own guarantee, that a bounded read is dense up to its bound or covers the whole log below it. A backend that answers short (a truncated read) leaves the request to the observation path instead of serving a page missing every event between the suffix tail and the bound. The opening window's plan carries neither `throughSeq` nor `beforeSeq`, so it reads unbounded exactly as before.

**A provider that ignores the bound never gets a silently wrong page.** The seek surface is structural, and every in-tree consumer now threads the bound and reports the observed end. An out-of-tree provider still implementing the released three-argument `readFrom(id, fromSeq, signal?)` receives the bound in its `signal` position: one that answers its released whole-tail read is refused loud by the validator (`gateway/internal`, the window past its bound) instead of being cut into a page, and one that reports no observed stored end is refused loud the same way. A provider that dereferences the bound as an `AbortSignal` throws inside the fast path, and the observation path answers the request — the released result, without the bound win. The repo is pre-stable; no route serves a page the bound did not cover.

**The consumer validates a bounded read against the stored end it observed.** `history.ts`'s validator receives the end in force and the observed stored end. A read bounded below the request cursor runs the released cursor checks against the stored end — a cursor above it fails `gateway/bad-request` with the released message, and a cursor the observed log cannot hold still fails the released internal check — while the bound itself answers the read's density check (a window that reached past its bound is `gateway/internal`). The released cursor checks stay verbatim for every unbounded read and for a bound above the cursor (which is the cursor plus one). This restores the released outcome for every request shape: `{throughSeq: 3000, beforeSeq: 901}` on a 1,200-event log is `gateway/bad-request` on both paths, as `tests/session-page-bound.host.spec.ts`'s shape battery pins.

**An absent bound is the released behavior.** Every new parameter is optional and last but for `signal`; `physicalSpanFrom` selects the released statement, the per-event filter collapses to the released `seq >= fromSeq`, and no plan passes a bound where it did not before. `tests/differential.spec.ts` pins the unbounded equality for every `fromSeq`.

## Alternatives considered

**Filter the whole-tail read in the caller instead of bounding the query.** That is the released behavior: the rows are already decoded by then, which is the cost being removed. The filter is still applied — it is what keeps a straddling packed row's members above the bound out of the result — but it cannot replace the predicate.

**Bound the SQL by the packed row's whole span (select the row whose END precedes the bound).** That would drop a row whose members below the bound are part of the page, producing a gap at every page that lands inside a packed run. The bound belongs on the first logical seq, and the members are filtered after the decode.

**Return the short suffix and let the caller detect the truncation.** The consumer cannot tell "the log ended below the bound" from "the read stopped early", so a short suffix would either be served as a page with a silent gap or rejected in the legitimate case of a log that shrank below the bound. The store owns the distinction at the only place with the rows to make it.

**Keep validating the bounded read against the request cursor.** The cursor is the client's own last-seen seq, not this read's contract: an older page ends below it by construction, so the check rejects exactly the reads this change exists to serve.

**Leave the bounded read's cursor unchecked.** That is the regression this change fixes: the fast path answered `{throughSeq: 3000, beforeSeq: 901}` on a 1,200-event log with `ok: true` while the observation path rejected it `gateway/bad-request`, silently accepting a desynced client cursor. The observed stored end costs one index-only query inside the read's own transaction.

**Make the bound a new `Config` field.** It is a per-call addressing value derived from the request, not a deployment-varying tunable; the plan already computes it.

## Consequences

An older page reads only the rows that can represent its own span; on a session whose pages sit deep in the log this removes the linear-in-depth decode while the served page is unchanged, which `tests/session-page-bound.host.spec.ts` and the two added `session-open-window.host.spec.ts` cases pin by comparing the fast path with the observation path. A bounded read additionally costs one index-only `MAX(seq)` inside its own read transaction, and only when a bound is given. The opening page (`beforeSeq` absent, cursor present) is bounded at cursor + 1: `paginateSuffix` filters its window to the same end either way, so the page and its acceptance are identical, and the read no longer decodes a live session's events past the client's cursor. Every request shape the bounded path can answer now fails exactly where the observation path fails: the shape battery in `tests/session-page-bound.host.spec.ts` compares the two paths' full results, including the reviewer's `{throughSeq: 3000, beforeSeq: 901}` on a 1,200-event log, `beforeSeq === throughSeq`, `throughSeq: -1`, `beforeSeq > throughSeq`, `{5000, 4000}`, and `beforeSeq` of 0 through 3.

One limitation is worth naming: a packed row's decoded members are retired `assistant/chunk` events, which `validateStoredEvents` refuses for a current-format row. Such a row is therefore only readable through the historical arm (whole-log restore) or through the statement-level view, which is why `tests/bounded-suffix-read.spec.ts` pins the straddle with a bound at the window start (empty result, no refusal) and one seq past it (the surviving member at the bound's predecessor is observable through the format refusal that names its seq), and `tests/bounded-suffix-statements.spec.ts` pins the row selection itself. The deployed store's current-format rows never contain packed rows; the fork's legacy rows take the historical arm, which `seekable` gates out of the fast path.
